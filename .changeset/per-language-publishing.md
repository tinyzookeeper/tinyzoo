Entities can publish each language on its own: add `perLocale: true` to an entity's `publish`. A translation then has a state and a schedule of its own (draft, published, scheduled), and the editor's Publish, Unpublish and Schedule act on the language being edited. The default language keeps its state on the entry, and a translation **follows it until someone publishes or unpublishes that language**, so turning the option on changes nothing on the website, for entries with a translation and for entries without one (served in other languages through the fallback) alike.

A language that is not published is not there: the item answers `404` with `?locale=` for it, and it is left out of that language's list, of the sitemap and its `hreflang` alternates, of the website search and of links (a link to it is `null` there, as for a draft). Inside a published translation, fields left empty still show the default language's text. An editor's `?preview` (or the content token) still sees the draft. **The default language gates every language:** a translation is on the website only while the default language is live too, so unpublishing the default language takes every language off (a language keeps its own state and applies it again when the default language is published), and a translation of a draft never shows the draft's shared fields or fallback text. A language can still be unpublished or scheduled on its own, and is then live from the later of its date and the default language's; a language that follows is live exactly when the default language is. Scheduled go-lives and unpublishing are announced per language: `entry.published` and `entry.unpublished` carry that language in `locale` and only its addresses in `paths` (the payload keeps its shape; fields are only added); a change to the default language names every language it takes along that has a translation or a state of its own, and when the default language goes live on its date the scheduler announces each language that was waiting for it too. The admin shows each language's state in the editor, the list, the dashboard and the search (a published language held back by a draft default language reads "Waiting for the default language"); whoever may not publish cannot publish, unpublish or reschedule a language, cannot remove a translation that holds a state of its own (the language would follow the default language and could go live), and cannot change a language that is marked published; the editor's read-only switch, shared editing and the save all judge a translation by its own state. Export and import, seeds (`translations: { en: { status: 'draft' } }`), the history of a language and its restore carry the state; an archive's content model says which entities publish per language, an archive without states (from 0.5) leaves the states already in a site alone on `--merge`, and one with states into a site that cannot keep them is reported (an archive from 0.6 with per-language states cannot be imported into 0.5 faithfully). `definePages({ perLocale: true })` turns it on for pages (not yet for page trees: the config check says so). `PATCH /api/cms/<entity>/<id>?locale=en` takes the entry's own status and date keys for it (`{ "status": null }` follows the default language again).

**Nothing changes for an entity that does not set `perLocale`**, and the content API's shape and `@tinyzoo/client`'s types are the same (the contract snapshots did not change).

### Upgrade

1. Only if you want it: add `perLocale: true` to the `publish` of an entity that has `.localized()` fields, run `tinyzoo generate` and commit the migration (two nullable columns on its `<entity>_locales` table: `published` and `published_at`), then `tinyzoo up`. There is no data to move and no upgrade step: every language starts by following the default one, so every page, list, sitemap entry and `hreflang` alternate stays as it is.
2. Without it, nothing: no migration, no change. If you do turn it on, note the default language's gate above: a language published while the default language is a draft waits for it, and a webhook receiver that purges by `paths` needs nothing new (unpublishing the default language names every language that went off).
3. Export and import between two sites: keep both on 0.6 when states are involved (0.5 drops them without a word).
